## 1. 一句话说明

A7Z 是**主控（上位机）**，通过 **BLE GATT** 连接这块灯控板（ESP32-C3），
用三个自定义特征完成「开关灯 / 逐灯 RGB / 读状态 / 收通知」。

**C3 侧是 Peripheral（GATT Server），A7Z 是 Central（GATT Client）。**

## 3. 硬件与连接信息

| 项 | 值 |
|---|---|
| 设备广播名 | `BTSH-LIGHT` |
| 设备 MAC（实测） | `DC:DA:0C:82:B8:6E`（**注意：这个会因芯片而异，不要写死，按名字过滤扫描**） |
| BLE 地址类型 | Public |
| 广播类型 | 可连接、可扫描（ADV_IND） |
| 广播数据 | Flags + **厂商自定义数据（能力声明）** |
| 扫描响应 | 含 Complete Local Name = `BTSH-LIGHT` |
| 连接间隔 | 系统协商 7.5ms → 稳定 48.75ms（正常，不需干预） |
| 认证/配对 | **不需要**（未启用加密，属性权限是 Open） |

> **重要**：扫描时**必须做主动扫描（Active Scan）**，因为设备名在**扫描响应**里。
> 但设备**身份**不需要名字——广播数据里就有厂商自定义数据（见 6.5 节），
> 被动扫描也能拿到，可用于"扫到即识别"。

## 4. 完整的 GATT 结构（实测确认）

服务：**16 位自定义 UUID `0xFF00`**
（不是 128 位！NuttX 的 `BT_GATT_PRIMARY_SERVICE` 宏硬编码 `BT_UUID_16`）

| 属性 | UUID | 句柄（实测编号，**不要写死**） | 权限 | 长度 |
|---|---|---|---|---|
| 主服务 | `0xFF00` | 0x0001 | — | — |
| 命令特征声明 | `0xFF00`→`0xFF01` | 0x0002 | — | — |
| **命令特征值** | `0xFF01` | 0x0003 | **WRITE / WRITE NO RESPONSE** | 1 或 4 字节 |
| 状态特征声明 | `0xFF01`→`0xFF02` | 0x0004 | — | — |
| **状态特征值** | `0xFF02` | 0x0005 | **READ + NOTIFY** | 1 字节 |
| 状态 CCC | `0x2902` | 0x0006 | 读/写 | 2 字节 |
| 设备信息声明 | `0xFF02`→`0xFF03` | 0x0007 | — | — |
| **设备信息值** | `0xFF03` | 0x0008 | **READ** | 3 字节 |

> 句柄编号只在**本次固件**有效。**请一律按 UUID 查找**，不要按句柄硬编码——
> 这也是 nRF Connect 日志里最容易看错的地方（写特征声明句柄 0x0002 是无效操作）。

## 5. 数据格式（**最关键的一节**）

### 5.1 命令特征 `0xFF01` —— 按写入长度区分语义

#### 格式 A：1 字节（简单开关）

| 字节 | 含义 |
|---|---|
| `0x00` | 关灯：5 颗全部熄灭 |
| `0x01` | 开灯：5 颗全部设为绿色 `(0, 40, 0)` |

#### 格式 B：4 字节（逐灯 RGB）

| 偏移 | 名称 | 取值 |
|---|---|---|
| 0 | `index` | `0..4` = 第几颗灯（0 基）；**`0xFF` = 整条灯带** |
| 1 | R | 0..255 |
| 2 | G | 0..255 |
| 3 | B | 0..255 |

**示例**（实测已验证第 3 条）：

```
00 40 00 00   → 第 1 颗灯 = 红（R=0x40）
01 00 40 00   → 第 2 颗灯 = 绿
FF 00 00 40   → 全部 = 蓝
FF 00 00 00   → 全部熄灭
```

### 5.2 状态特征 `0xFF02`

**1 字节的聚合状态**：

| 值 | 含义 |
|---|---|
| `0x00` | 全灭（5 颗都全黑） |
| `0x01` | 至少有一颗亮着 |

> 注意：它**不回读每颗灯的颜色**。要记录颜色，请自己在 A7Z 侧维护一份影子状态。

### 5.3 设备信息 `0xFF03`

3 字节，固定值：

| 偏移 | 含义 | 值 |
|---|---|---|
| 0 | 协议版本 | `0x01` |
| 1 | 通道数 | `0x01` |
| 2 | 保留 | `0x00` |

**用途**：连接后第一件事读它，等于 `01 01` 就确认「对端是 BTSH 灯控、协议版本匹配」。

## 6. 标准交互时序（照这个实现就行）

```
1. 主动扫描，过滤广播名 == "BTSH-LIGHT"
2. 建立连接（不需要配对）
3. 服务发现，按 UUID 定位 0xFF00 及三个特征值 + CCC
4. 【必做】写 CCC(0x2902) = 01 00        ← 不写这一步收不到任何通知
5. 读 0xFF03，校验 == 01 01 00           ← 确认协议版本
6. 读 0xFF02，拿到当前开关状态
7. 控制：
     开灯     → 写 0xFF01 = [01]
     关灯     → 写 0xFF01 = [00]
     逐灯设色 → 写 0xFF01 = [index, R, G, B]
8. 等待 0xFF02 的 Notify（1 字节），用它更新 UI 上的开关状态
```

### 6.1 时序上的注意事项

- **第 4 步必须在所有读写之前**，否则第 8 步永远收不到数据。
- 写 `0xFF01` 建议用 **Write Request（需要响应）**，这样能确认写入成功；
  用 Write Without Response 也可以，但你不会知道失败。
- 写完命令后，**状态通知会紧跟着到达**（实测时间差 < 100ms）。

## 6.5 免连接识别（v1.1 新增，强烈建议用）

固件在**广播数据**里塞了一段厂商自定义数据（Manufacturer Specific Data），
A7Z **不用连接**就能识别设备类型与能力：

```
广播: 02 01 06 | 07 FF | FF FF | 01 | 01 | 05 | 07
                     └ 类型  └ID   └ver └类型 └灯数 └能力位
```

| 字段 | 值 | 含义 |
|---|---|---|
| Company ID | `0xFFFF`（小端 FF FF） | BT SIG 保留给测试；量产需申请正式 ID |
| 协议版本 | `0x01` | 与 `0xFF03` 的第 1 字节一致 |
| 设备类型 | `0x01` | RGB 灯控 |
| 灯珠数量 | `0x05` | 与 `0xFF03` 的第 2 字节语义对应（通道数） |
| 能力位 | `0x07` | bit0 开关 / bit1 逐灯RGB / bit2 通知 |

**推荐扫描逻辑**：

```
扫到广播 → manufacturer_data[0xFFFF] 存在 && payload[1] == 0x01
        → 判定为本项目灯控，读取灯珠数量与能力位
        → 直接连接（不需要靠名字猜）
```

这样能避免连错设备、自动生成 UI，也不需要先连接试探。
详见 `BLE_PROTOCOL_A7Z.md` §10。

## 7. 参考实现

### 7.1 可执行规范：`port/tools/ble_client.py`

这是我在 C3 侧写的一个 PC 端工具，**逻辑与 A7Z 需要做的完全一致**，
可以直接当伪代码读。关键片段：

```python
BTSH_SERVICE_UUID = "0000ff00-0000-1000-8000-00805f9b34fb"
BTSH_CMD_UUID     = "0000ff01-0000-1000-8000-00805f9b34fb"   # WRITE
BTSH_STATE_UUID   = "0000ff02-0000-1000-8000-00805f9b34fb"   # READ + NOTIFY
BTSH_INFO_UUID    = "0000ff03-0000-1000-8000-00805f9b34fb"   # READ

# 开关（1 字节）
await client.write_gatt_char(BTSH_CMD_UUID, bytes([0x01]))
# 逐灯 RGB（4 字节）
await client.write_gatt_char(BTSH_CMD_UUID, bytes([index, r, g, b]))
# 读状态
await client.read_gatt_char(BTSH_STATE_UUID)
# 订阅通知
await client.start_notify(BTSH_STATE_UUID, callback)
```

### 7.2 A7Z 侧（C 语言 / 各家 BLE 栈）的映射关系

无论 A7Z 用的是哪套 BLE 协议栈，对应关系都是：

| 本协议动作 | 通用 BLE 栈对应操作 |
|---|---|
| 扫描 | start scan（**主动扫描**）→ 过滤 `local_name == "BTSH-LIGHT"` |
| 连接 | connect（LE，不需要 bonding） |
| 服务发现 | discover primary services → 找 `0xFF00` |
| 找特征 | discover characteristics of `0xFF00` |
| 写 CCC | write descriptor `0x2902`，value = `0x0001`（小端 `01 00`） |
| 写命令 | write characteristic `0xFF01`，1 或 4 字节 |
| 读状态/信息 | read characteristic `0xFF02` / `0xFF03` |
| 收通知 | 注册 `0xFF02` 的 notify 回调 |

## 8. 踩过的坑（**请务必读完，能省你几小时**）

这些是我在 C3 侧上板后遇到的真实问题，其中前两条**会直接导致"连上了但什么都做不了"**。

### 8.1 对端"能连上但不理你"可能是对端的协议栈 bug

C3 侧最初的固件有两个协议栈 bug，表现出来的现象是：

```
能广播 → 能连接 → 服务发现超时 → 30 秒后断开
```

**已经被我修好**（`port/apply-stack-fixes.sh`）。但如果 A7Z 侧也遇到类似现象，
先怀疑**你自己这一侧的协议栈**，而不是对端不配合。

### 8.2 `ERROR_GATT_CONN_TIMEOUT` / `Error 133` 通常是"对端没应答"

Android 上的 `Error 133 (0x85) GATT ERROR` + 紧接着 `Error 8 GATT CONN TIMEOUT`，
在本次调试中的真实原因是**对端（C3）在写 CCC 的瞬间崩溃了**，不是手机的问题。

### 8.3 扫描不到设备名

- 必须用**主动扫描**（设备名在扫描响应里）
- Android 需要**"附近设备"权限**，没有权限会一个设备都扫不到
- 有些系统会缓存设备名，改名后需要清缓存或换手机

### 8.4 写操作别打到"特征声明"

GATT 里每个特征有两个属性：**声明（declaration）** 和 **值（value）**。
写命令必须写到 `0xFF01` 的**值**属性（实测句柄 0x0003），
写到声明属性（0x0002）会得到错误或被忽略。**按 UUID 查找就能避免这个坑。**

### 8.5 亮度别开满

5 颗 WS2812B 全白满亮度（255,255,255）电流约 300mA，接近 USB 供电上限，
可能出现灯闪或板子复位。**建议 0..64，40 已经很亮。**
