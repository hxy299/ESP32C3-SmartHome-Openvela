# BLE 通信协议（A7Z 对接文档）

> 下位机：ESP32-C3-SmartHome-Actuator（openvela）
> 上位机：A7Z 开发板（作 BLE Central / GATT Client）
> 服务实现：`apps/wireless/bluetooth/btsh_light/btsh_light_main.c`

---

## 1. 角色分配

| 角色 | 板子 | BLE 角色 |
|---|---|---|
| 下位机（被控） | ESP32-C3-SmartHome-Actuator | **Peripheral / GATT Server**（广播 + 提供服务） |
| 上位机（主控） | A7Z | **Central / GATT Client**（扫描 + 连接 + 读写） |

ESP32-C3 上电后在 NSH 里执行 `btsh_light start` 才会开始广播。

---

## 2. 广播参数

| 项 | 值 |
|---|---|
| 设备名（ADV name） | **`BTSH-LIGHT`**（可用 `CONFIG_BTSH_LIGHT_ADV_NAME` 改） |
| 广播类型 | 可连接、可扫描（connectable undirected） |

A7Z 侧按名字 `BTSH-LIGHT` 扫即可。

## 3. GATT 服务结构

自定义 **16 位** UUID（NuttX 的 `BT_GATT_PRIMARY_SERVICE()` 只支持 16 位，不支持 128 位）。

| 属性 | UUID | 属性句柄 | 权限 | 长度 | 说明 |
|---|---|---|---|---|---|
| 主服务 | **`0xFF00`** | `0x0001` | — | — | 灯控服务 |
| 命令特征声明 | `0xFF01` | `0x0002` | — | — | — |
| **命令特征值** | `0xFF01` | `0x0003` | **WRITE** | 1 或 4 | 见 §3.1 |
| 状态特征声明 | `0xFF02` | `0x0004` | — | — | — |
| **状态特征值** | `0xFF02` | `0x0005` | **READ + NOTIFY** | 1 | 0x00=全灭，0x01=有灯亮 |
| 状态 CCC | `0x2902` | `0x0006` | 读写 | 2 | 写 `0x0001` 开启通知 |
| 设备信息声明 | `0xFF03` | `0x0007` | — | — | — |
| **设备信息值** | `0xFF03` | `0x0008` | **READ** | 3 | 见下 |

### 3.1 命令特征值（0xFF01）两种写入格式

**格式 A —— 1 字节（兼容旧协议）**

| 值 | 含义 |
|---|---|
| `0x00` | 关灯（全部熄灭） |
| `0x01` | 开灯（全部设成绿色 `(0,40,0)`） |

**格式 B —— 4 字节（逐灯 RGB）**

| 偏移 | 名称 | 说明 |
|---|---|---|
| 0 | index | `0..4` = 第几颗灯（0 基）；**`0xFF` = 整条灯带** |
| 1 | R | 0..255 |
| 2 | G | 0..255 |
| 3 | B | 0..255 |

下位机按**写入长度**区分格式，所以两种写法可以共存，老代码不用改。

> 亮度建议先用 0..64 试，40~64 已经很亮；5 颗全白满亮度（255）会接近 USB 供电上限。

### 3.2 状态特征值（0xFF02）语义

1 字节的**聚合状态**：任意一颗灯非全黑 → `0x01`，全部全黑 → `0x00`。
逐灯颜色请以自己写入的值为准（本协议不回读每颗灯的颜色）。


### 设备信息（0xFF03）3 字节

| 偏移 | 名称 | 值 |
|---|---|---|
| 0 | 协议版本 | `0x01` |
| 1 | 通道数 | `0x01` |
| 2 | 保留 | `0x00` |

## 4. A7Z 侧交互流程

```
1. 扫描广播，找到 name == "BTSH-LIGHT"
2. 建立连接
3. 发现服务 0xFF00
   ├─ 找到特征 0xFF01 (Write)
   ├─ 找到特征 0xFF02 (Read/Notify) + 其 CCC (0x2902)
   └─ 找到特征 0xFF03 (Read)
4. 读 0xFF03 → 期望 {01 01 00}，确认对端是 BTSH 灯控
5. 写 CCC(0x0006) = 0x0001 → 开启状态通知
6. 写 0xFF01 = 0x01  → 开灯
   写 0xFF01 = 0x00  → 关灯
7. 每次状态变化会收到 0xFF02 的 Notify（1 字节）
```

### 最小验证序列（只要三步）

```
读 0xFF03  → 01 01 00        证明 GATT 通了
写 0xFF01  → 01              灯亮
读 0xFF02  → 01              状态一致
```

## 5. 下位机侧（ESP32-C3）操作

串口（UART0，115200）进 NSH：

```
nsh> btsh_light start      # 注册 GATT 服务并开始广播
nsh> btsh_light state      # 查看状态、UUID、广播名、LED 设备
nsh> btsh_light stop       # 停止广播并关灯
nsh> btsak                 # 蓝牙瑞士军刀：scan / advertise / gatt 操作
```

`btsh_light state` 的正常输出类似：

```
BTSH light service
  service UUID : 0xff00
  cmd   UUID   : 0xff01 (write)
  state UUID   : 0xff02 (read/notify)
  info  UUID   : 0xff03 (read)
  adv name     : BTSH-LIGHT
  LED device   : /dev/leds0 (fd=3)
  light state  : OFF
```

**关键**：`fd=3` 表示 `/dev/leds0` 打开成功，即 WS2812 驱动已注册。若 `fd=-1`，说明灯带驱动没起来（检查 `CONFIG_WS2812`、`CONFIG_ESPRESSIF_SPI2`、`CONFIG_ESPRESSIF_SPI2_MOSIPIN=4`）。

## 6. 常见问题

| 现象 | 原因 / 排查 |
|---|---|
| A7Z 扫不到 `BTSH-LIGHT` | 下位机没执行 `btsh_light start`；或 BLE 控制器没起来（看启动日志有没有 BLE 初始化失败） |
| 连上后写 0xFF01 无反应 | 写到了特征声明句柄（0x0002）而不是特征值句柄（0x0003） |
| 收到通知但灯不变 | 看 `btsh_light state` 的 `light state` 是否跟着变；不变则是 cmd 处理没触发 |
| `fd=-1` | WS2812 驱动未注册，检查 SPI2 / MOSIPIN=4 配置 |
| 灯颜色异常 | `CONFIG_WS2812_FREQUENCY` 应为 8000000（4-bit 编码，落在 5.9–9MHz 区间） |

## 7. 逐灯 RGB 使用示例

```python
# A7Z 侧（伪代码）：第 1 颗红、第 2 颗绿、全部熄灭
write(0xFF01, [0x00, 64,   0,  0])     # 第 1 颗 -> 红
write(0xFF01, [0x01,  0,  64,  0])     # 第 2 颗 -> 绿
write(0xFF01, [0xFF,  0,   0,  0])     # 全部熄灭
```

PC 端可直接用仓库工具验证逐灯寻址是否正确：

```bash
python port/tools/ble_client.py --rainbow      # 每颗灯一个颜色
python port/tools/ble_client.py --rgb 0 64 0 0 # 只改第 1 颗
```

### 为什么先跑 `--rainbow`

5 颗灯如果颜色顺序/数量不对（比如只亮前 2 颗、或颜色错位），一眼就能看出来——
这比逐个写单色快得多，也能顺带确认 WS2812 数据线的方向（DIN 从哪颗进）。

## 8. 备注：为什么是 16 位 UUID

NuttX 的 `BT_GATT_PRIMARY_SERVICE()` 宏内部把服务属性 UUID 类型硬编码为 `BT_UUID_16`
（见 `include/nuttx/wireless/bluetooth/bt_gatt.h`），**当前实现无法声明 128 位服务 UUID**。
所以这里用自定义的 16 位 UUID `0xFF00`，并避开了 Bluetooth SIG 已分配的常用值。

如果 A7Z 侧用现成的 BLE 调试 App，只要能手工填 16 位 UUID 就都能对接。

## 9. 实测验证记录（2026-10-22，手机 nRF Connect 实测）

以下每一步都是**真实跑通**的，A7Z 侧可以按同样的时序实现。

| # | 对端动作 | 实测结果 |
|---|---|---|
| 1 | 扫描 `BTSH-LIGHT` | ✅ 能扫到，RSSI 约 -10 ~ -32 dBm（贴板测试） |
| 2 | 建立连接 | ✅ `le_conn_complete status 0`，角色 = 外设 |
| 3 | 服务发现 | ✅ 发现 `0xFF00` 及下属 4 个特征/描述符 |
| 4 | 读 `0xFF03` | ✅ 返回 `01 01 00` |
| 5 | 读 `0xFF02` | ✅ 返回 `00`（全灭状态） |
| 6 | 写 CCC `0x2902` = `01 00` | ✅ 成功，回 `Notifications enabled` |
| 7 | 写 `0xFF01` = `00 40 00 00` | ✅ **第 1 颗灯变红** |
| 8 | 状态变化通知 `0xFF02` | ✅ 能收到 `01` |

### 9.1 A7Z 侧实现时的注意事项（血泪教训）

1. **必须先写 CCC 再等通知**，否则收不到任何 notify。
2. **写入长度决定语义**：1 字节 = 开关；4 字节 = `[index, R, G, B]`。
3. `index` 用 `0xFF` 表示整条灯带，`0..4` 表示单颗。
4. **MTU 交换请求要处理但不必强求**：对端（本板）会正常应答 MTU 交换；若你的中央设备不发起也可以，默认 MTU 23 足够跑本协议（最大 4 字节写入）。
5. **亮度建议 0..64**：40 已经很亮；5 颗全白满亮度（255）会接近 USB 供电上限。
6. 连接间隔实测：系统会协商到 7.5ms 然后稳定在 48.75ms，属正常。

### 9.2 已知限制

- 本板连续连接约 8 次后需要复位（协议栈 `bt_conn` 槽位回收不完整的已知问题）。A7Z 如需长时间反复重连，请在固件侧复现时留意。

## 10. 广播格式与"免连接识别"（v1.1 新增）

中心设备**不需要建立连接**，就能从广播里知道对端是什么设备、有多少灯、支持哪些操作。
这实现了官方宣传里"无缝发现"的效果，且完全基于标准 BLE 广播，不依赖任何私有协议。

### 10.1 广播数据（ADV_IND，共 11 字节）

```
02 01 06                           ← Flags: LE General Discoverable | BR/EDR Not Supported
07 FF FF FF 01 01 05 07            ← Manufacturer Specific Data（厂商自定义）
```

逐个字节：

| 字节 | 值 | 含义 |
|---|---|---|
| `02 01 06` | — | EIR 长度 2 / 类型 0x01(Flags) / 值 0x06 |
| `07` | 7 | EIR 长度 = 1(type) + 6(数据) |
| `FF` | 0xFF | EIR 类型 = Manufacturer Specific Data |
| `FF FF` | 0xFFFF | **Company ID（小端）** ⚠️ BT SIG 保留给测试用途，量产须申请正式 ID |
| `01` | 1 | 协议版本 |
| `01` | 1 | 设备类型：`1` = RGB 灯控 |
| `05` | 5 | 灯珠数量 |
| `07` | 0x07 | 能力位（见下） |

### 10.2 能力位定义

| bit | 掩码 | 含义 |
|---|---|---|
| 0 | `0x01` | 支持 1 字节开关命令 |
| 1 | `0x02` | 支持 4 字节逐灯 RGB 命令 |
| 2 | `0x04` | 支持状态通知（Notify） |

本固件上报 `0x07` = 三项全支持。

### 10.3 扫描响应（Scan Response，共 12 字节）

```
0B 09 42 54 53 48 2D 4C 49 47 48 54   ← 0B 09 + "BTSH-LIGHT"
```

### 10.4 A7Z 侧的扫描逻辑（推荐实现）

```
1. 主动扫描
2. 只认 manufacturer_data[0xFFFF] 存在、且 payload[1] == 0x01（设备类型=灯控）的广播
      → 这就是"扫到即识别"，不需要连接、不需要看名字
3. payload[2] → 灯珠数量，用来动态生成 UI（几个滑块/几个色轮）
4. payload[3] → 能力位，决定哪些功能可用
5. 需要人可读名字时，再看 scan response（"BTSH-LIGHT"）
6. 然后按第 6 节时序连接、开通知、下发命令
```

**这样做的三个好处**：

- **不会连错设备**：只连身份字段匹配的目标
- **UI 自动适配**：灯珠数量和能力位由设备上报，写死配置就没了
- **发现更快**：一次扫描就能列出所有兼容设备，无需逐个连接试探

### 10.5 兼容性说明

| 情况 | 行为 |
|---|---|
| 旧固件（v1.0，无厂商数据） | 只能靠名字 `BTSH-LIGHT` 识别 |
| 新固件（v1.1） | 名字 + 厂商数据双保险 |
| 想保持通用 | 先按厂商数据识别，找不到再退回按名字匹配 |
